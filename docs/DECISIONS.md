# Decisions

Ambiguities and the call made, one line each. Repositories made from this template keep this file and add their own rows below.

## Template foundation

| # | Question | Decision | Why |
|---|----------|----------|-----|
| 1 | What the template is for | A GitHub template repository that a new project starts from. It carries governance (rulesets, code owners, PR policy), security (secret scanning, pinned supply chain, least-privilege CI) and AI-agent guardrails (Claude Code settings, a guard hook, CLAUDE.md, AGENTS.md) as files, plus scripts that apply and audit the GitHub-side settings | Settings that live only in the GitHub UI drift and cannot be reviewed. Files can be diffed, reviewed in a PR and tested |
| 2 | Single source of truth | `governance/policy.json` lists the required files, required checks, repo settings, security features and PR rules. Scripts and tests read it; nothing repeats it | One place to change a rule. `tests/Template.Tests.ps1` fails when the ruleset, the workflows and the policy disagree |
| 3 | Branch protection: classic branch protection or rulesets | A repository ruleset (`governance/rulesets/main.json`) targeting `~DEFAULT_BRANCH` | Rulesets are GitHub's current model: they stack, can be exported and imported as JSON, and the same payload works for an organization ruleset later |
| 4 | Ruleset contents | PR required; 1 approval; code owner review; stale approvals dismissed on push; the last push must be approved by someone else; conversations resolved; squash only; linear history; no force push; no deletion; required checks `lint`, `test`, `workflow-lint`, `secret-scan`, `dependency-review`, `pr-policy` from GitHub Actions only (`integration_id` 15368), branch up to date before merge | The usual production baseline. Pinning the checks to the GitHub Actions app stops another app or a commit status from faking a green check |
| 5 | Solo maintainers and the approval rule | Repository admins may bypass the ruleset **only through a pull request** (`bypass_mode: pull_request`). They cannot push to `main` directly | A one-person repo cannot get an approval from someone else, so without a bypass nothing could merge. The bypass still forces a PR, so checks run and the change is recorded. Teams delete the `bypass_actors` entry (one line) |
| 6 | Signed commits | Not required by default | Agent sessions and some CI bots cannot sign today, so requiring it blocks the agent workflow. Add `{ "type": "required_signatures" }` to the ruleset when every committer signs |
| 7 | Private repositories on GitHub Free | Supported, with honest gaps: rulesets, secret scanning, push protection and dependency review need GitHub Pro, Team or Advanced Security on private repos. `Set-RepoGovernance.ps1` reports each refusal as a warning; `Test-RepoGovernance.ps1` reports it as Warn, not Fail. The `dependency-review` job runs only on public repos (a skipped required check counts as passed) | The template must work on the cheapest plan without pretending a control is on when it is not |
| 8 | Script language | PowerShell 7, the same as sk-devops-svc and gitops-platform. Every `gh` and `git` call goes through `Invoke-Cli` in `scripts/lib/Cli.ps1` | Runs on Windows locally and Linux in CI. One wrapper means Pester can mock every external call, so tests need no network or token |
| 9 | Why `gh api` and not Terraform's GitHub provider | `gh api` with JSON payloads from `governance/` | No state file to store or lock, nothing else to install, and the payloads are the exact REST bodies GitHub documents. Terraform suits an organization managing hundreds of repos; the payloads can move there unchanged |
| 10 | Applying settings safely | `Set-RepoGovernance.ps1` supports `-WhatIf`, updates a ruleset by name instead of creating a second one, and is safe to run twice | Settings changes are hard to review after the fact. A dry run shows every call first |
| 11 | CI shape | Three workflows: `ci` (lint, test, workflow-lint), `security` (secret-scan, dependency-review), `pr-policy` (title and body). Job ids equal the required check names | Separate workflows can be re-run on their own, and a required check name never changes when a workflow is renamed |
| 12 | Third-party actions | Only `actions/checkout`, `actions/upload-artifact` and `actions/dependency-review-action`, each pinned to a commit SHA. Tools (actionlint, gitleaks) are downloaded from their releases and checked against the published SHA-256; zizmor is installed with `pip --require-hashes` | Each third-party action is code running with the job's token. A SHA cannot be moved like a tag. Checksums turn a tampered download into a failed job |
| 13 | Workflow security | Top-level `permissions: contents: read`, `persist-credentials: false` on every checkout, `timeout-minutes` on every job, never `pull_request_target`, PR title and body passed only through `env:`. `tests/Template.Tests.ps1` fails the build if any of these is broken; zizmor checks the rest | These are the common ways a workflow leaks a token or runs attacker-controlled text. A test makes them hold for every future workflow, not just today's |
| 14 | Secret scanning tool | gitleaks 8.30.1 over the full history on every PR, every push to `main` and weekly, with `--redact` | Works on private repos on any plan, catches secrets in old commits, and never prints the secret it found |
| 15 | PR policy | Conventional Commit titles and five required body sections (What changed, Why, How it was verified, Risk and rollback, AI assistance), checked by `scripts/Test-PullRequest.ps1`. More than 60 changed files is a warning | The squash commit takes the PR title and body, so `main`'s history stays readable. The AI assistance section makes agent work visible to reviewers |
| 16 | Dependabot | GitHub Actions ecosystem, weekly, one grouped PR, `ci:` prefix, 7-day cooldown | One PR a week is reviewable. The cooldown avoids taking a release in its first days, when compromised releases are usually caught |
| 17 | AI agent guardrails | Four layers: `.claude/settings.json` deny and ask rules; a PreToolUse guard hook; the same CI and ruleset as humans; human review through CODEOWNERS. Paths that change the rules (workflows, governance, agent settings) always need a human to confirm | No single layer is enough. The deny list is easy to get around with a different spelling, so the hook and CI back it up, and the ruleset is enforced by GitHub where the agent has no say |
| 18 | Guard hook failure mode | If the hook cannot read its input it allows the call and writes a note to stderr | A broken hook must not stop every session. CI and the ruleset still apply, so a fail-open hook loses one layer, not all |
| 19 | Agent working method | The orchestrate skill ships in `.claude/skills/orchestrate/`: brief, plan, parallel subagents with an explicit model and effort, verify, report | Every repo made from the template starts with the same way of working, so results are comparable and verified |
| 20 | License | MIT | Permissive and short. Change it in repos that need another license |
